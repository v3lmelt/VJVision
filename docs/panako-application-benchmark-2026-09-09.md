# Panako 常驻 WSL 服务与当前 Windows 识别对照

后续已完成 Windows 原生适配并修复删除队列，见 [原生运行验证](panako-native-windows-2026-09-09.md)。本报告保留未修复版本的 WSL 对照结果。

测试日期：2026-09-09。应用基线为 `cd05bcfe018ab005c0448c10e05c60ccc24a4252`。本次实现 Windows Python 经常驻进程管道调用 WSL 内 Panako，使用持久化 LMDB，将传输和识别成本计入当前应用的真实确认循环。部署通路与复现步骤见 [Windows 接入说明](panako-windows-integration.md)。

Panako 在本批调速输入上有明确收益：两类加速切歌均为 6/6 成功，原速切歌和叠歌的中位等待也更短。代价是 6 秒音频处理成本增加约 27%，首歌中位等待增加约 3.23 秒。Windows 经 WSL 的调用已经实测可行，但发现的原生索引删除故障需要绕开或修复，当前不能当作完成了生产替换。

## 环境与实验边界

本机 AMD Ryzen 7 5800H，Windows Python 3.11.15；WSL Ubuntu 使用 Temurin Linux JRE 11.0.32.1 和官方 `Panako-2.1-all.jar`。Java 桥接以 Java 11 目标编译，JVM 最大堆设为 2 GiB，这个设置不代表实测内存占用。应用没有停止，处理耗时仍受本机负载影响。

参考歌曲与 Olaf 受控 benchmark 完全相同：6 首可解码且已索引的真实歌曲，通过原文件 SHA-256 校验。Dejavu 使用独立的六首曲库副本，Panako 对相同的整首音频重新建立 LMDB。当前库中其余 117 首参考音频不在可用素材中，不能据此推断完整曲库下的性能。

三组分别为当前 Dejavu、同接受条件 Dejavu、Panako WSL。当前 Dejavu 的生产识别函数保持不变；后两组采用至少 20 个对齐命中、跨越至少 2 秒、领先下一首候选至少两倍的条件。接受与弱候选分别转换为接口数值 0.30 和 0.06，供现有状态机读取，并非校准的概率。

Panako 每次查询重算指纹，没有跨窗口复用。其内部最短匹配跨度固定为 1.5 秒，其余原生参数重置为 JAR 的默认值。此配置沿用此前原型，本次没有针对失败样本调整参数。

应用仍使用 6 秒短窗口、12 秒后备窗口、2 秒稳定轮询、1.25 秒候选轮询、10% 时间扰动、连续两次切歌确认和 0.75 秒位置容差。Panako 的参考位置按照返回的速度比例换算到查询窗口末尾，避免把变速输入当成原速位置。

Panako 的匹配票数与 Dejavu 的去重指纹数含义不同；提前通过短窗口时，Panako 的比例字段使用原生时间覆盖率，Dejavu 使用查询指纹支持比例。形式相同的门槛不能解释为相同的误报概率。对照组用于观察判定条件的影响，不能完全隔离所有算法差异。

## Windows 调用与处理成本

建库后关闭整个 Java 工作进程，再启动新进程查询同一片段，候选列表、匹配数、位置和速度比例完全一致。WSL 已启动时，工作进程重启到就绪约 1.82 秒；未测 WSL 从关闭状态启动的时间。

30 次空请求往返耗时中位约 0.248 毫秒，P95 约 0.483 毫秒。6 秒音频查询中，管道传输及消息处理的配对额外耗时中位约 0.598 毫秒。此数字按每次请求的 Windows 往返耗时减去 Java 核心查询耗时后求中位数，不能用两个独立中位数相减替代。

以下每种长度包含 18 个完全相同的输入窗口，覆盖每首歌的第 30、70、110 秒位置。计时从 48 kHz 双声道 PCM 输入开始，包含重采样、PCM 转换、传输、原生识别与结果转换；不包含首次建库或 JVM 初始化。

| 输入窗口 | 当前 Dejavu 中位 | Panako WSL 中位 | 当前接受正确数 | Panako 接受正确数 |
| --- | ---: | ---: | ---: | ---: |
| 2 秒 | 33.42 ms | 18.59 ms | 9/18 | 0/18 |
| 4 秒 | 52.95 ms | 48.18 ms | 9/18 | 0/18 |
| 6 秒 | 67.82 ms | 86.28 ms | 12/18 | 18/18 |
| 12 秒 | 123.05 ms | 199.98 ms | 11/18 | 18/18 |

单窗口接受正确数使用 0.30 接口门槛，不代表应用首歌的 0.25 门槛。短窗口处理快但不能确认歌曲，不能因此宣称短片段识别速度更快。6 秒查询的完整计算路径比当前 Dejavu 慢约 27%，主要成本在分析而非 WSL 通信。

本轮对当前 Dejavu 重新计时，没有复用之前 Olaf 报告中的数值。不同运行批次的墙钟耗时会变化，不应把此前约 11 毫秒的 Olaf DLL 与本表直接当作同轮精确速度排名。

## 连续场景的定义

三组分别运行同样的 108 个场景，每次观察 36 秒，模拟时钟计入真实识别墙钟耗时与循环等待。输入与轮询随机种子固定，组别执行顺序打乱。

- 原速直接切歌、8 秒交叉淡化、次要歌曲引入后撤回、首歌开始，各 18 个场景。
- 静音和噪声合计 6 个场景。
- 加速 6% 且改变音高、保留音高加速 6%、300–5000 Hz EQ，各 6 个场景。
- 逐首留出目标歌曲，测试未知歌曲直接输入和从已知歌曲切入，各 6 个场景。Dejavu 从独立副本中删除目标，Panako 每次重新建立仅含其余五首歌的独立 LMDB，并另查目标的 12 秒片段确认没有泄漏。

直接切歌发生在第 5 秒，延迟从该时刻计算。交叉淡化从第 5 秒开始，到第 13 秒结束，延迟从第 9 秒的等增益点计算；从淡化动作开始计算需加 4 秒。首歌从音频开始计算。保留音高加速使用 FFmpeg `atempo=1.06`，并非对全部 DJ 软件 Key Lock 算法的复现。

测试运行真实 `MatcherThread.run()`，替换音频设备、元数据及画面输出。电平检测固定为活跃；不包含麦克风、声卡、封面、视觉淡入淡出、文件解码及建库时间。未完成实体 DJ 设备和打包 EXE 验证。

## 连续识别结果

原速场景各组均成功 18/18。下表为确认延迟中位数 / P95，单位秒：

| 场景 | 当前 Dejavu | 同接受条件 Dejavu | Panako WSL |
| --- | ---: | ---: | ---: |
| 直接切歌 | 10.71 / 24.69 | 9.98 / 12.14 | 7.39 / 10.40 |
| 8 秒交叉淡化 | 10.51 / 15.89 | 9.37 / 14.21 | 7.35 / 9.89 |
| 首歌开始 | 1.97 / 10.67 | 2.70 / 5.38 | 5.20 / 5.42 |

Panako 的直接切歌中位确认时间缩短约 31%，交叉淡化缩短约 30%；首歌中位时间增加约 3.23 秒。这里比较各组中位数，并非所有配对片段均更快。Panako 原速直接切歌单次计算比当前路径慢，但较稳定的匹配证据让这批场景更早通过确认。

| 变换切歌 | 当前成功数 | 同条件 Dejavu 成功数 | Panako 成功数 | Panako 中位 / P95 |
| --- | ---: | ---: | ---: | ---: |
| 加速 6%，音高随之变化 | 0/6 | 0/6 | 6/6 | 8.57 / 15.59 秒 |
| 保留音高加速 6% | 4/6 | 6/6 | 6/6 | 7.77 / 22.11 秒 |
| EQ 带通 | 6/6 | 6/6 | 6/6 | 7.73 / 14.34 秒 |

Panako 在本轮调速输入上明显减少未确认，但并非每次都快。保留音高加速的一次切换用了 26.22 秒，同条件 Dejavu 在该类场景的 P95 为 13.26 秒。当前 Dejavu 的该类延迟统计仅有四个成功样本，不能忽略其余两个失败后直接比较平均速度。

18 次过渡撤回中，同接受条件 Dejavu 有一次先切到次要歌曲、之后又恢复原歌：模拟时间 12.21 秒切换，19.89 秒恢复。它的最终歌曲正确数为 18/18，但全过程无误切的正确数为 17/18。此事件保留在结果中，没有针对它调参。评估索引和接受规则必须同时查看中途事件，不能只看最后显示哪首歌。

| 保持或拒绝识别场景 | 当前全过程正确 | 同条件 Dejavu 全过程正确 | Panako 全过程正确 |
| --- | ---: | ---: | ---: |
| 过渡撤回 | 18/18 | 17/18 | 18/18 |
| 静音与噪声 | 6/6 | 6/6 | 6/6 |
| 未入库歌曲直接输入 | 6/6 | 6/6 | 6/6 |
| 已知歌曲切入未入库歌曲，保留原显示 | 6/6 | 6/6 | 6/6 |

最终三个组各完成 108 个场景，共 324 次循环。Panako 本轮没有错误歌曲切换、提前切换或确认后回退；这不代表大曲库和真实混音环境下的误报率为零。所有已记录切换事件均在 36 秒观察区间内，生产源码哈希在测试后保持一致。

## 索引删除失败与后续处理

首轮在完成 288 次非留出场景后，尝试原生 LMDB 删除。随后查询返回 `metadata unavailable!`，使桥接程序在解析歌曲 ID 时失败。检查上游 `PanakoStorageKV.processDeleteQueue()`，并用 `javap` 检查实际 JAR 字节码，确认它检查和读取的是 `storeQueue`，而非 `deleteQueue`。元数据删除成功，指纹却残留，因此无法把这次删除当成有效的留出实验。

未修改上游识别算法，也未把异常当成“未知歌曲识别正确”。后续采用六个独立的五首曲库完成留出测试，通过 `--resume-negatives` 保留原有 288 次结果并追加最后 36 次循环。入口校验歌曲、生产源码及 JAR 哈希，拒绝混入不同版本。正常从头运行也采用独立重建方式。

这项结果表明，当前版本的原生删除流程不能直接用于正式曲库维护。可先使用后台重建新索引、验证后切换的方式；针对上游删除函数的修复和回归测试属于后续工作。重建时间未计入逐窗口识别成本。

## 接入取舍

对于当前 DJ 调速需求，Panako 值得进入下一阶段的应用集成验证。保留现有首歌快速路径，在后台常驻 Panako 服务，有机会兼顾首歌响应与调速识别；这种组合尚未运行对照，不能把本次单引擎结果直接当作组合方案的结果。

正式接入前优先完成索引安全重建、服务异常恢复，以及真实音频采集测试。随后扩大独立歌曲数量，增加减速、不同 Key Lock 算法和混音方式。本轮没有重新测减速或单独变调的连续场景，旧的独立片段结果不能替代这些验证。
