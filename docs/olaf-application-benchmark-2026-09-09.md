# Olaf 与当前歌曲识别的受控对照测试

测试日期：2026-09-09。当前基线为 `cd05bcfe018ab005c0448c10e05c60ccc24a4252`。

Olaf 常驻 DLL 确实减少了计算耗时，原速直接切歌也更快。但首歌确认中位时间增加，保留音高调速的成功率下降，现有证据不足以支持全面替换生产引擎。此次仅增加离线 benchmark，应用仍使用 Dejavu。

## 测试范围与可比性

- 本机 AMD Ryzen 7 5800H，Windows，Python 3.11.15，Zig 0.16.0。
- 使用本地曲目目录中可解码且已有指纹的 6 首真实 MP3，每首取 30、70、110 秒处的片段。未使用无法解码的 NCM。
- 当前数据库有 123 首记录，但其余参考音频不在本次可用文件中。因此，两组都使用相同的 6 首参考曲库。Dejavu 从现有数据库的独立备份中筛选，Olaf 用相同的整首歌曲重新建立索引。
- 每组运行 108 个连续音频场景，共 324 次真实 `MatcherThread.run()` 循环。每次观察 36 秒，模拟时钟计入实际识别计算耗时和轮询等待。
- 另对 72 个完全相同的音频窗口测量处理成本，覆盖 6 首歌、3 个位置、2/4/6/12 秒长度，每个长度有 18 个样本。三种调用方式的运行顺序使用固定随机种子打乱。
- 输入统一为 48 kHz 双声道 PCM。保留各引擎必需的预处理，Dejavu 使用当前应用路径，Olaf 转为 16 kHz 单声道。
- 沿用当前 6 秒短窗口、12 秒后备窗口、2 秒稳定轮询、1.25 秒候选轮询、10% 时间扰动，以及连续确认、位置连续性和保留原歌曲规则。
- 不包含声卡、麦克风、封面加载、界面绘制、音频文件解码、建库和引擎首次初始化耗时。模拟音频电平检测固定为活跃，静音仍进入识别函数检查，不能视为实际采集链路的耗电测试。

设置三组以帮助区分引擎与判定规则的影响：

| 组别 | 识别与判定路径 |
| --- | --- |
| current_dejavu | 当前应用的 Dejavu 识别函数和置信度原样保留 |
| common_gate_dejavu | Dejavu 对齐证据，使用与 Olaf 相同形式的接受条件 |
| olaf_dll | Olaf 原生对齐结果，通过内存 DLL 接入同一应用循环 |

后两组沿用前次原型的条件：至少 20 个对齐匹配、至少跨越 2 秒、领先下一首候选至少两倍。本次没有根据结果调参。强弱判定分别转换为接口数值 0.30 与 0.06，供现有状态机读取；这些数值不代表经过校准的置信概率。

Dejavu 的证据按查询指纹去重，Olaf 使用原生匹配票数，两者密度和重复计数语义不同。应用跳过长窗口时仍检查 20% 支持比例，但分子的定义不同。第三组对照能显示判定规则的影响，不能证明双方具有相同的误报概率。

## 相同窗口的计算成本

下表为从输入 PCM 到返回识别结果的墙钟耗时中位数，单位毫秒。DLL 保持数据库和 FFT 计划常驻，CLI 包含临时查询音频写入和进程启动成本。

| 输入长度 | 当前 Dejavu | Olaf CLI | Olaf DLL |
| --- | ---: | ---: | ---: |
| 2 秒 | 22.34 | 37.03 | 3.95 |
| 4 秒 | 40.18 | 40.82 | 7.82 |
| 6 秒 | 57.71 | 43.32 | 10.97 |
| 12 秒 | 105.27 | 57.13 | 22.14 |

6 秒窗口的 DLL 计算耗时减少约 81%，吞吐速度约为当前路径的 5.3 倍。每个窗口仍重新提取指纹，尚未实现跨窗口增量提取。

对 72 个窗口逐一核对原生 CLI 与 DLL：指纹总数、候选歌曲及匹配数全部一致；时间跨度和位置允许 CLI 输出两位小数造成的 0.021 秒误差。72/72 检查通过。DLL 仅替换文件读取为内存读取，使用未修改的上游提取器和匹配器。

六首曲库的主索引文件分别为 Dejavu 10,625,024 字节、Olaf 1,564,672 字节，后者减少约 85%。不包含映射数据库、锁文件、运行库及二进制程序，也未测量峰值内存或建库时间。

## 连续识别的确认延迟

每个单元格为中位数 / P95，单位秒。各组以下三类均成功 18/18，未发现提前切换、错误歌曲切换或确认后退回原歌曲。

| 场景 | 当前 Dejavu | 同接受条件 Dejavu | Olaf DLL |
| --- | ---: | ---: | ---: |
| 原速直接切歌 | 10.61 / 16.26 | 9.12 / 11.83 | 6.40 / 8.47 |
| 8 秒交叉淡化 | 9.37 / 19.17 | 9.78 / 13.55 | 8.60 / 12.27 |
| 从静音开始首歌 | 1.95 / 7.43 | 3.83 / 7.64 | 3.93 / 6.44 |

直接切歌在模拟时间第 5 秒发生，延迟从切歌动作开始计算。交叉淡化从第 5 秒持续到第 13 秒，延迟从两首歌曲增益相等的第 9 秒计算；若从淡化开始计算，表中数值需要增加 4 秒。首歌延迟从音频开始计算。

Olaf 直接切歌中位时间缩短约 40%，交叉淡化缩短约 8%。这些是各组中位数的变化，并不表示每一个配对片段都更快。部分淡化片段仍出现 Olaf 比当前版本慢的情况。

首歌中位时间增加约 1.98 秒。采用相同接受条件的 Dejavu 同样变慢，说明至少 2 秒证据跨度等规则对首歌速度有明显影响。不能把整个差异都归因于原生引擎。

每次 36 秒直接切歌场景内，识别函数累计墙钟耗时中位数从 2.507 秒降到 0.314 秒。该数字不包含其他应用工作，也不等于整个程序的 CPU 占用率。原始数据保留进程 CPU 时间，但 Windows 计时粒度导致部分短调用显示零，因此不据此宣称零 CPU 开销。

## DJ 变换与负样本

变换施加在进入的下一首歌曲上，每种变换包含 6 对歌曲，使用 70 秒处音频。成功表示在观察时间内最终确认目标歌曲；未确认会继续保留原歌曲。

| 场景 | 当前 Dejavu | 同接受条件 Dejavu | Olaf DLL |
| --- | ---: | ---: | ---: |
| 加速 6%，同时改变音高 | 0/6 | 0/6 | 0/6 |
| 加速 6%，保留音高 | 4/6 | 6/6 | 1/6 |
| EQ 带通 300–5000 Hz | 6/6 | 6/6 | 6/6 |
| 引入次要歌曲后退出，保留原歌曲 | 18/18 | 18/18 | 18/18 |
| 静音与噪声，无错误确认 | 6/6 | 6/6 | 6/6 |
| 未入库歌曲，无错误确认 | 6/6 | 6/6 | 6/6 |
| 已知歌曲切到未入库歌曲，保留原歌曲 | 6/6 | 6/6 | 6/6 |

保留音高的加速使用 FFmpeg `atempo=1.06`，这是离线近似，不代表所有 DJ 软件的 Key Lock 算法。EQ 场景的确认延迟中位数为当前 14.27 秒、同条件 Dejavu 11.07 秒、Olaf 6.95 秒。保留音高调速有不同数量的未确认样本，不应只比较成功样本的延迟来评价速度。

未入库测试逐首从双方的独立测试索引中移除目标歌曲，完成查询后恢复；每首都测试直接输入和从已知歌曲切入。所有 324 次循环中上述错误事件计数为零，但变速场景仍有未确认。这些结果不能写成全部识别成功，也不足以估计大曲库的低误报率。

## 本次取舍

原速播放、直接切歌和受 EQ 影响的片段有明确收益，值得继续作为可选引擎验证。对于需要调速的 DJ 使用方式，当前 Olaf 配置存在实测退步，应先解决调速容错，再考虑替换默认引擎。

计算已缩短到十毫秒量级，确认仍需要数秒，后续优化应同时检查证据积累时间和确认规则。首歌条件需要单独验证，不能仅降低所有切歌门槛。下一阶段应扩大独立曲目数量、覆盖真实 DJ 输出和更多调速比例，并在可比较的误切水平下重新评估。
