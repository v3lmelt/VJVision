# 歌曲识别引擎比较与对齐确认

本轮比较显示，Panako 在变速和变调的识别准确率上更有优势，Olaf 更适合短片段识别。应用本次采用兼容现有指纹库的对齐确认改进。两种候选引擎仍属于离线原型，尚未接入应用的索引、采集和打包流程。

## 素材与环境

使用用户提供的 6 首可解码 MP3，另一个 NCM 文件未参与测试。曲目来自真实文件，但样本仅有 6 首，多次取片段不代表增加了独立歌曲数量。机器为 AMD Ryzen 7 5800H，Windows、Python 3.11.15、NumPy 1.26.4、SciPy 1.17.1。原应用仍在运行，耗时会受机器负载及采样相位影响。

片段引擎比较使用相同的 6 首参考歌曲，均建立独立索引或使用副本。应用版本对照使用完整的 123 首歌曲、641657 条指纹的 SQLite 副本，原库和音频文件不变。素材没有上传。

## 片段识别结果

各歌曲从第 30、70、110 秒取样，每类 18 个片段。Dejavu 使用 PR #3 合并版本 `c1a72c892c98735ad1b44370f329143f185b0e85`，固定以 0.30 为单次接受门槛；这与应用首歌 0.25 的门槛有区别。Olaf 使用 C 核心默认参数。Panako 的最短匹配跨度从默认 5 秒调整到 1.5 秒，其余算法参数保留发布版默认值。

| 输入 | Dejavu 正确数 | Olaf 正确数 | Panako 正确数 |
| --- | ---: | ---: | ---: |
| 原速 2 秒 | 9/18 | 13/18 | 0/18 |
| 原速 4 秒 | 9/18 | 15/18 | 0/18 |
| 原速 6 秒 | 12/18 | 16/18 | 18/18 |
| 原速 12 秒 | 12/18 | 17/18 | 18/18 |
| 加速 6%，音高随之变化，6 秒 | 0/18 | 0/18 | 16/18 |
| 减速 6%，音高随之变化，6 秒 | 0/18 | 1/18 | 11/18 |
| 保持音高加速 6%，6 秒 | 7/18 | 18/18 | 17/18 |
| 升高一个半音并保持时长，6 秒 | 0/18 | 3/18 | 18/18 |
| 300–5000 Hz 带通 EQ，6 秒 | 9/18 | 17/18 | 18/18 |
| 加入约 20 dB 信噪比白噪声，6 秒 | 4/18 | 18/18 | 18/18 |

所有表内失败均为未达到接受条件，未返回错误歌曲。全静音、随机白噪声和同一首库外歌曲的三个位置共 5 个负样本，三个引擎均未误报。Panako 内存存储的删除接口未实现，验证工具使用查询排除集合，在候选排序之前排除留出的曲目；原生索引和 SQLite 副本则实际删除该曲目。

默认 Panako 最短跨度为 5 秒时，本批 6 秒片段均未通过，12 秒原速片段为 18/18。调整后仍无法识别本批 2 秒和 4 秒片段，因此不能把变速鲁棒性直接当成更低的采样等待时间。

6 秒原速片段的处理时间中位数约为 Dejavu 49 ms、Olaf 52 ms、Panako 99 ms。Olaf 包含重采样、写入查询 PCM 和启动原生进程，Panako 使用常驻 JVM、内存索引和预解码 PCM，并在本机 WSL 中运行。这些耗时没有统一运行边界，不能作为严格的计算速度排名。它们也不包含积累 6 秒音频的等待。

## 候选引擎的连续 DJ 原型

第 30 和第 70 秒两组素材，各有 6 组循环配对。每组构造直接切换、8 秒线性交叉渐变、第二声道最高增益 0.35 后撤回，合计 36 个场景。

两引擎都使用最近 6 秒、每 2 秒查询一次的相同观测时间点。原型要求至少 20 个匹配、覆盖 2 秒、领先第二候选至少两倍，并且连续两次通过，才改变当前歌曲。不同引擎的匹配计数含义仍有差异，这套门槛只用于原型比较。

| 场景 | Olaf | Panako |
| --- | --- | --- |
| 直接切歌 | 12/12，确认中位 7 秒 | 12/12，确认中位 7 秒 |
| 渐变叠歌 | 12/12，确认中位 9 秒 | 12/12，确认中位 8 秒 |
| 过渡撤回 | 12/12 保持原曲 | 12/12 保持原曲 |

没有无关曲目切换或早于参考点的切换。直接切换从第 5 秒开始计时，渐变从两个声道增益相等的第 9 秒计时。连续场景保留原速，调速验证使用前面的独立片段测试。时间不计计算、音频硬件、元数据及画面淡入淡出；原型只有 6 首参考歌曲，因此不能与下方完整应用测试的时间直接相减。

## 本次应用改进

- 单次 SQL 查询同时生成原有匹配结果与时间对齐证据，保留现有数据库格式和原有置信度含义。
- 在相邻三个时间偏移格内，按查询指纹的哈希与时间去重。参考歌曲中重复出现的同一哈希，不会反复增加这一份查询证据。
- 最近 6 秒中的候选达到原有置信度门槛，并满足至少 20 个去重命中、占查询指纹 20%、覆盖 2 秒、领先第二首歌两倍，才能免去长窗口核验。
- 提前确认仍需要原有次数的独立采样。连续近期命中的播放位置需要随时间推进，允许 0.75 秒误差；位置突然跳变会重新计数。
- 其他情况保留 12 秒核验。弱证据不增加次数，冲突、无结果、采集重置和异常清除待确认记录。
- 内存识别返回的歌曲偏移改用当前实际 FFT 步长 3072 帧换算，避免沿用 Dejavu 导入时的默认步长。

这项改进降低的是证据明确时的确认等待。计算对齐证据需要额外的集合运算，无法解决原有指纹对变速和变调的敏感性。首歌接受规则与刷新频率保持原有配置。

## 完整应用对照

以 PR #3 合并提交为基线，运行真实 `MatcherThread.run()` 和完整曲库副本。第 30、70 秒素材各使用采样种子 7、29，第 110 秒素材使用新的种子 83。每个版本共 129 个场景，两版本合计 258 次模拟。每个场景观察 36 秒，采集输入模拟为 48 kHz 双声道；虚拟时钟计入真实匹配计算耗时，未接入实体音频设备，也不计封面读取和画面淡入淡出。

| 场景 | 基线成功数 | 新版成功数 | 基线确认中位 | 新版确认中位 | 基线 P95 | 新版 P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 直接切歌 | 29/30 | 30/30 | 11.56 秒 | 9.62 秒 | 21.12 秒 | 19.88 秒 |
| 渐变叠歌 | 25/30 | 30/30 | 11.68 秒 | 10.92 秒 | 19.87 秒 | 18.84 秒 |
| 首歌获取 | 30/30 | 30/30 | 1.39 秒 | 1.44 秒 | 5.83 秒 | 7.87 秒 |
| 过渡撤回 | 30/30 | 30/30 | 保持原曲 | 保持原曲 | — | — |
| 静音、噪声与库外曲目 | 9/9 | 9/9 | 无误报 | 无误报 | — | — |

全部场景均未出现无关歌曲切换、提前切换、确认后回退或撤回过渡时误切。时间统计只纳入成功场景，不给超时样本虚构耗时。对于两版都成功的配对样本，直接切歌有 19/29 更快，中位差为减少 0.72 秒；叠歌有 18/25 更快，中位差为减少 1.13 秒。不同片段仍有变慢的情况，不能保证每次切换都提前。

首歌没有获得稳定提速，P95 反而增加约 2 秒。旧指纹对采样起点敏感，计算与调度的小幅变化可能改变后续命中；这是本轮保留的限制。更换引擎和流式复用需要另行验证，不能用本轮对齐确认结果承诺秒级首歌响应。

每个 36 秒场景累计匹配墙钟时间的中位数如下，不能直接解释为整机 CPU 占用率：

| 场景 | 基线 | 新版 |
| --- | ---: | ---: |
| 直接切歌 | 3.40 秒 | 3.03 秒 |
| 渐变叠歌 | 3.63 秒 | 3.25 秒 |
| 过渡撤回 | 2.54 秒 | 2.72 秒 |
| 首歌获取 | 2.41 秒 | 2.40 秒 |
| 随机白噪声 | 5.33 秒 | 5.37 秒 |
| 库外音乐 | 5.56 秒 | 5.90 秒 |

提前确认可以省去部分长窗口查询，但始终不满足提前确认条件的场景仍会承担对齐集合计算。新版本以切歌成功率和部分场景的等待改善，换取这些额外开销。

45 项单元测试、Python 编译检查和差异检查通过。新增检查覆盖重复参考位置去重、相邻时间格、歌曲之间的证据隔离、SQL 旧结果一致性、提前确认条件及播放位置跳变。第 110 秒完整对照记录的六个应用模块 SHA-256 与最终代码一致。未修改打包配置，未生成新版 EXE，未声称完成实体混音台测试。

## 复现

Windows 原生 Olaf C 核心使用 [Olaf](https://github.com/JorenSix/Olaf) 提交 `532f1991ba170b39d2156b43935428814e833614`，通过 Zig 0.16.0 的 C 编译器构建。使用 Makefile `compile_core` 列出的 C 源文件，生成 64 位 Windows 程序；旧 MinGW 6.3 构建失败，未用于测量。测试工具要求该核心使用独立工作目录内的 `db`，检测到会改用用户主目录的 `HOME` 环境变量时拒绝执行。

[Panako](https://github.com/JorenSix/Panako/releases/tag/joss) 使用官方 `Panako-2.1-all.jar`，SHA-256 为 `767cdd2cd0991658c4a25a0b8e887f9a2a38f69ae17781b02fe1652e1a7173d4`。Windows 启动因 JGaborator 原生库缺失失败；测量使用本机 Ubuntu WSL 和 Temurin JRE 11.0.32.1。Java 桥接程序用 JDK 11 编译，直接读取预解码 16 kHz 单声道 PCM，避免解码子进程影响结果。

```powershell
python tools/compare_recognition_engines.py --baseline-ref c1a72c8 --olaf cache/engine-olaf/olaf_core.exe
javac -cp cache/engine-panako/Panako-2.1-all.jar -d cache/engine-panako tools/PanakoComparison.java
python tools/compare_engine_transitions.py --olaf cache/engine-olaf/olaf_core.exe
```

在能够加载 JGaborator 的 Java 环境中，将 JAR 和编译后的桥接目录加入 classpath，运行 `PanakoComparison`，依次传入 `cache/engine-comparison-data/manifest.tsv` 或 `dj-manifest.tsv`，以及最短跨度 `1.5`。Linux 的 classpath 分隔符为冒号。桥接输出保存后，运行：

```powershell
python tools/compare_recognition_engines.py --panako-log cache/panako-short-verified.log
python tools/compare_engine_transitions.py --panako-log cache/panako-dj.log
python tools/benchmark_dj_transitions.py --baseline-ref c1a72c8 --offset 30 --seeds 7 29 --output cache/aligned-final-30.json
python tools/benchmark_dj_transitions.py --baseline-ref c1a72c8 --offset 70 --seeds 7 29 --output cache/aligned-final-70.json
python tools/benchmark_dj_transitions.py --baseline-ref c1a72c8 --offset 110 --seeds 83 --output cache/aligned-final-110.json
python -m unittest discover -s tests -v
python -m compileall -q main.py vjvision tools
```

原始片段比较保存在忽略提交的 `cache/engine-comparison.json`，Panako 结果在 `cache/panako-short-verified.log`，连续原型结果在 `cache/native-dj.json`。工具不会上传歌曲。源音频、原生程序、JAR、运行时和数据库均不提交到仓库。

## 后续引擎选择

如果继续重构，Panako 值得作为 DJ 调速与调音高场景的主要候选，Olaf 值得作为短片段快速通道。下一步需要解决 Windows 原生依赖、索引迁移与恢复，并实现真正的流式特征复用；本轮原型每次仍重新分析一个窗口。

当前 123 首曲库中只有 6 首源文件仍能访问，直接替换索引无法保留其余歌曲的识别能力。本次合并的对齐确认可继续使用所有旧指纹。候选引擎的六首歌测试不足以证明大曲库误报率和所有叠歌方式下的可靠性，尚不作为应用默认依赖。
